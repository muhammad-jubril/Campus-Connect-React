# Campus Connect Notifications — frontend/backend contract

This document is the integration contract for the frontend. It intentionally adds **no database migration** and does not create a second notification schema.

## Existing contract inspected in the repository

The current client-facing table used by the existing SQL triggers is `public.notifications`, with the known fields `id`, `recipient_id`, `actor_id`, `type`, `post_id`, `read`, and `created_at`. The existing notification type constraint currently permits only `like` and `comment`. Existing trigger logic creates notifications for post likes and comments on the post author; replies and follows are not covered by the inspected trigger migration.

The frontend reads rows from this existing table using `select("*")`, filters reads by `recipient_id`, updates only the `read` flag for that recipient, fetches actor display fields from `public.profiles`, and subscribes to Supabase Realtime changes on the same table filtered to the signed-in recipient.

## Types and target information needed

The existing `like` and `comment` type rows can be consumed now if the live project has the expected table policies and Realtime publication.

To support the complete requested feature, backend-generated rows should use canonical `type` values `like`, `comment`, `reply`, and `follow` (aliases are accepted by the UI for compatibility). In addition to the current fields, supply the relevant target fields the real schema supports:
- `post_id` for likes and comments, and for replies when a reply belongs to a post.
- `comment_id` or `thread_id` for replies. This is required to group replies by the correct thread instead of merging replies on unrelated comments.
- `profile_id` / `target_id` / `target_type` only if that matches the backend's actual schema; these are optional hints supported by the frontend, not a request to create redundant fields.

The client never inserts generated notifications. Likes, comments, replies, and follows should continue to be generated by backend-owned triggers/functions. Grouping exists only in the frontend presentation layer; all underlying activity IDs are retained so users can mark one event, a group, or all events as read.

## Realtime

Enable the existing notifications table for Supabase Realtime/Postgres Changes in the backend deployment and retain recipient-scoped RLS. The frontend listens for all changes filtered to `recipient_id=eq.<authenticated-user-id>` and refreshes the list/count after each event. If the channel cannot subscribe, the page shows that live updates are unavailable and provides a manual Refresh button.

## Read-state operations

- `UPDATE public.notifications SET read = true WHERE id = :id AND recipient_id = auth.uid()` for one event.
- Same update filtered by a list of IDs for individual events within a group.
- Same update filtered by `recipient_id = auth.uid() AND read = false` for Mark all as read.

Keep the existing RLS/policies and column privileges as the authority. The frontend filters by recipient too, but this is not a substitute for backend security.

## Push subscriptions (only active after backend setup)

Configure these frontend environment variables after the backend endpoint is deployed:
- `VITE_WEB_PUSH_PUBLIC_KEY`: the public VAPID key only (never a private key).
- `VITE_PUSH_SUBSCRIPTION_ENDPOINT`: the HTTPS endpoint which owns subscription persistence.

The endpoint must authenticate the `Authorization: Bearer <Supabase access token>` header and derive the user ID from that token, never from a client-supplied user ID. Required idempotent operations:
- `POST` with `{ "subscription": PushSubscriptionJSON }` to create/attach a new subscription.
- `PUT` with the same payload to synchronize an existing browser subscription.
- `DELETE` with `{ "endpoint": "<push endpoint>" }` to remove the caller's subscription.
- Return a 2xx response only after persistence/removal has succeeded; return a useful error status and `{ "error": "..." }` when it has not.

The frontend shows push as enabled only after the backend confirms a `POST`/`PUT`. If the endpoint or VAPID key is missing, it clearly shows that setup is not connected and disables the enabling action rather than faking success.

Push payloads should send a JSON body such as `{ "title": "Campus Connect", "body": "Ibrahim liked your post", "data": { "url": "/post/<id>" } }`; optional `icon`, `badge`, and `tag` are also supported. The worker shows the push payload as a system notification and uses `data.url` for click navigation. `public/push-sw.js` is imported into VitePWA's generated worker through `workbox.importScripts`, not registered independently; its handlers reject cross-origin targets and focus/navigate an existing same-origin app window when possible.

## Backend security checklist

1. Recipient RLS prevents other users from selecting/updating notifications.
2. Client can update only `read`, not actor, recipient, type, target, or review metadata.
3. Generation excludes self-notifications and respects mutual-blocking rules once the backend adds follow notifications.
4. Replies resolve to their specific comment/thread and do not masquerade as top-level post comments.
5. Follow rows have the actor ID so profile navigation can resolve the actor's username.
6. Realtime is enabled without broadening authenticated table reads.
