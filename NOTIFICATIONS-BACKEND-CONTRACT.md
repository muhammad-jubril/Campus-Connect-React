# Campus Connect Notifications — backend contract after independent audit

This document describes the existing notification model and the forward backend pipeline. Do not treat source-level/static tests as proof of a deployment against the live Supabase project.

## Existing event model verified in the repository

The existing client-facing table is `public.notifications`, with known fields `id`, `recipient_id`, `actor_id`, `type`, `post_id`, `read`, and `created_at`. The checked-in type constraint and triggers originally generated only `like` and `comment`. Notifications are generated by database triggers, not inserted by the React client. Recipient-scoped `notifications_select_own` and `notifications_update_own` policies are present in the hardening migration; authenticated updates are limited to `read` by the lockdown migration.

The relationship extension migration `supabase/migrations/20261012140543_notifications_relationships.sql` adds `comments.parent_comment_id`, the `public.follows` relation and the missing notification targets without creating a second notification table or push queue. The frontend still needs to wire the existing comment composer to supply `parent_comment_id` for replies and its follow control to use the follow RPC contract below; these integration points are listed below for the frontend agent.

## Canonical row and write contract

The existing frontend continues to read `public.notifications` and resolve actors from `public.profiles`. The complete server-generated activity row has these target/source fields in addition to the original columns:

- `source_id`: identity of the triggering row. Likes use `likes.activity_id`; comments and replies use `comments.id`; follows use `follows.id`. A unique partial index prevents one source activity from creating duplicate recipient/type notifications.
- `comment_id` and `thread_id`: for replies, **both contain the root (top-level) comment ID**. The immediate reply parent is stored on the source `comments.parent_comment_id`. The frontend grouping helper currently prefers `comment_id`, so this avoids accidentally grouping only immediate siblings.
- `profile_id`: for follows, the profile being followed (the notification recipient).

Source write expectations for the frontend agent:

- Like: insert only `post_id` and authenticated `user_id`; the backend assigns a unique `activity_id`. An unlike/re-like creates a fresh like row and a distinct notification event.
- Top-level comment: use the existing comment flow and leave `parent_comment_id` null.
- Reply: send the parent comment ID as `parent_comment_id`; the database verifies that the parent belongs to the same post and that the author pair is not blocked.
- Follow/unfollow: call `follow_student({ p_following_id })` and `unfollow_student({ p_following_id })`. Do not mutate `public.follows` directly; the RPC derives identity from `auth.uid()`. `follow_student` returns `true` only when a new row is created and `false` when already following. `unfollow_student` returns `true` only when the caller's outgoing row was removed; repeated unfollow returns `false`.
- Never insert into `public.notifications` from the client. The backend triggers set actor/recipient/type/targets and preserve individual source rows.

The frontend already groups in-app follows by UTC day. Push follows are coalesced for the recipient's own profile during the quiet window. Likes/comments use the post as the target; replies use the root thread.

## 60-second push quiet window

Each newly created supported notification persists first in `public.notifications`, independently of push. The existing `public.push_notification_queue` is a push-only aggregation/outbox and is coalesced under a database advisory transaction lock. The database-owned `public.notification_push_config` is seeded with `enabled = false` and `quiet_window_seconds = 60`; keep it disabled until push secrets, Edge Functions, the scheduler, and a real-device delivery test are verified. The live Campus Connect project was enabled after its controlled browser delivery test succeeded. Change the quiet-window setting as needed (accepted range: 1–3600 seconds). The first event fixes the deadline, and activity arriving while the group is pending increments its count without moving that deadline. Once a batch is claimed for delivery, later activity starts a new pending group. Push-queue exceptions are caught in the trigger and logged as a warning so they do not roll back the notification/activity transaction. A one-minute scheduler may add up to approximately one minute of scheduling latency after the minimum quiet window.

The dispatcher claims due rows with `FOR UPDATE SKIP LOCKED`, uses per-subscription delivery receipts so retries skip already acknowledged subscriptions, applies backoff (30 seconds, 2 minutes, 5 minutes, then 10 minutes), stops after five worker attempts, and removes push endpoints returning HTTP 404/410. Web Push acceptance is not an exactly-once guarantee: if a push provider accepts a message and a subsequent database receipt write fails, a retry can still occur. A stable notification `tag` reduces duplicate visible alerts on supported browsers.

## Security

- Push subscription registration must send both `Authorization: Bearer <Supabase access token>` and `apikey: <VITE_SUPABASE_ANON_KEY>` in direct browser `fetch` requests. The bearer token authenticates the signed-in user; the public project key identifies the project and is safe in the `apikey` header. The backend validates the access token with `auth.getUser` and derives the owner ID; request bodies cannot choose an owner ID. Never send a service-role/secret key to the browser.
- Subscription endpoints are restricted to HTTPS and a list of known browser push-provider hosts, and key material is validated before persistence.
- Endpoint registration serializes both endpoint ownership and user subscription quota, prevents transferring an endpoint already owned by another account, and limits each account to ten subscriptions.
- The subscription, queue, and receipt tables have RLS enabled and no grants to `PUBLIC`, `anon`, or `authenticated`. Service-role-only RPCs are called by Edge Functions after their own authorization checks.
- The dispatch function requires gateway JWT authorization and validates the custom dispatch secret against Vault through a service-role-only RPC. It reads VAPID credentials from Vault only after that validation; the private key is never exposed to browser roles or Vercel.
- Notification generation and the dispatcher both check bilateral blocking. Recipient notification SELECT RLS also hides rows from currently blocked actors while preserving the underlying records. The dispatcher rechecks recipient-specific `hidden_posts` before delivering a post-target push. Reporting alone does not hide content; only the app's explicit content-visibility rules should suppress a target.

## Followers/following RPC contract

The single persistent relationship source is `public.follows`. It has a primary key, foreign keys to `public.profiles`, `UNIQUE (follower_id, following_id)`, and `CHECK (follower_id <> following_id)`. Its existing `AFTER INSERT` trigger `follows_notify_recipient` calls `public.notify_on_follow_relationship()` to create one source-keyed row in the existing `public.notifications` table. This migration does not create another notification system.

Authenticated mutations must use these RPCs. Direct authenticated INSERT/DELETE privileges on `public.follows` are revoked; the existing SELECT RLS remains involved-user-only.

| RPC | Input | Result |
|---|---|---|
| `follow_student` | `{ p_following_id: profileId }` | Boolean: `true` for a new relationship, `false` if already following. Rejects self-follow, missing profiles, and blocked pairs. |
| `unfollow_student` | `{ p_following_id: profileId }` | Boolean: `true` if the caller's outgoing row was removed, `false` if absent. No notification. |
| `get_follow_counts` | `{ p_profile_id: profileId }` | One-row table with `followers_count`, `following_count`, `is_following`, and `is_followed_by`. Counts exclude relationship edges that are currently blocked. |
| `get_followers` | `{ p_profile_id, p_limit = 20, p_offset = 0 }` | Paginated profile rows with `id`, `username`, `name`, `avatar_url`, `faculty`, `department`, `level`, `bio`, `followed_at`, `is_following`, `is_followed_by`. |
| `get_following` | Same arguments as `get_followers` | Same profile shape; newest relationships first. |

List queries return at most 100 rows per call. They reject unauthenticated requests and profiles blocked from the caller, and hide relationship entries with an active block in either relevant direction. Follow mutations only create/remove the caller's own outgoing edge. The unique constraint remains the final concurrency guard; only a successful INSERT fires the existing notification trigger, with `follows.id` as `notifications.source_id`.

Frontend usage:

```js
const { data: created, error } = await supabase.rpc("follow_student", {
  p_following_id: profileId,
});
const { data: removed, error } = await supabase.rpc("unfollow_student", {
  p_following_id: profileId,
});
const { data: rows, error } = await supabase.rpc("get_follow_counts", {
  p_profile_id: profileId,
});
const counts = rows?.[0]; // RETURNS TABLE returns an array
const { data: followers, error } = await supabase.rpc("get_followers", {
  p_profile_id: profileId, p_limit: 20, p_offset: 0,
});
```

`get_following` takes the same arguments as `get_followers`. List RPCs return an array of profile rows. For authorization failures, show a neutral “profile unavailable” state rather than inferring whether a blocked profile exists.
